# OpenCompete 真实产品经理使用记录（第一轮）

## 1. 测试结论

本轮使用了真实模型供应商配置和真实本地持久化目录，以产品经理身份发起“GitHub Copilot 与 Cursor 竞品分析”。范围确认、任务创建、失败留痕、历史任务查询和跨进程恢复均真实完成；模型供应商的推理接口持续返回 HTTP 502，研究在“生成研究简报”阶段被外部服务阻断，因此本轮**没有生成报告，也没有完成报告闭环**。

这不是一份成功演示记录。它记录的是产品在真实外部故障下的实际表现：任务没有丢失且可以恢复，但错误提示、恢复引导、进度展示和预算口径不足以让普通产品经理独立判断下一步。

## 2. 用户身份与目标

- 用户身份：需要为团队选择 AI 编程工具的产品经理。

- 分析层级：产品与服务。
- 关注维度：核心能力、定价、目标用户、购买决策。
- 预期结果：得到一份带来源、证据、明确对比和购买建议的可查看报告。
- 使用环境：Windows 本地 CLI、SQLite Checkpoint、本地产物目录；不启动 Agent Server，不依赖 Studio、LangSmith 或 MCP。

## 6. 产品经理视角的实际评价

### 做得好的部分

1. **先确认范围再研究。** 用户可以在产生主要研究成本之前确认对象、层级和维度。
2. **外部服务失败时任务不消失。** 任务编号、范围和失败记录都保存在本地。
3. **可以恢复同一个任务。** 不需要复制问题或重新创建任务，符合长耗时研究产品的基本预期。
4. **错误信息经过脱敏。** 记录中没有密钥、请求头和供应商响应正文。
5. **不依赖 Agent Server。** 创建、恢复和查询均由本地 CLI、SQLite 与本地产物完成。

### 阻碍真实用户的部分

1. **失败后不知道下一步。** “模型 Provider 暂时不可用”没有告诉用户任务已保存、是否可恢复、推荐等待多久或应执行什么命令。
2. **健康检查结论不准确。** 模型列表接口成功，但实际推理仍失败；仅检查 `/models` 会给出错误的恢复信号。
3. **报告不可查看时提示过于技术化。** “任务业务产物无法读取”应改为“该任务尚未生成报告；当前停在生成研究简报阶段，可稍后恢复”。
4. **缺少运行进度。** 真实研究可能持续数分钟，当前用户看不到正在进行的阶段、已完成步骤和预估剩余工作。
5. **失败调用的预算口径容易误导。** 清单把 6 次失败尝试按估算最大输出累计为 24,000 output tokens 和 0.20388 美元，但 `usage_source` 是 `estimated`。这不是供应商实际账单，界面必须明确区分“保守预算占用”和“已确认实际消耗”。
6. **自定义 OpenAI 兼容地址需要手工补 `/v1`。** 真实测试配置提供的是供应商根地址，完整链路需在当前进程临时补充 `/v1`；正式 CLI 与真实测试辅助逻辑不一致。
7. **终端表格截断信息。** 历史列表会截断任务编号，范围确认中的长维度也可能被终端宽度截断。

## 7. 问题优先级与建议

| 优先级 | 问题 | 建议的最小改动 | 不改的后果 |
|---|---|---|---|
| P0 | 自定义兼容地址处理不一致 | 把已经存在于 live 测试中的安全 `/v1` 地址选择能力接入正式 Provider 初始化，并补单元测试 | 用户配置看似正确但正式 CLI 无法调用模型 |
| P1 | 失败后缺少恢复引导 | 对可重试错误显示任务编号、当前阶段和完整 `resume` 命令 | 用户可能重复建任务或认为数据已丢失 |
| P1 | 健康检查只验证模型列表 | 使用一次极小的真实生成请求判断推理面是否恢复，限制输出并明确可能产生费用 | 系统过早提示恢复，用户重复失败 |
| P1 | 估算消耗与实际消耗混在一起 | 分开展示“已确认消耗”“失败调用保守占用”“剩余预算”；失败后释放未实际确认的输出预算或明确其计算语义 | 用户误判费用，预算可能被失败重试耗尽 |
| P1 | `show` 对未产出任务缺少状态解释 | 读取 manifest 后输出当前状态、失败阶段、是否可恢复和下一步命令 | 用户无法判断报告是丢失还是尚未生成 |
| P2 | 缺少阶段进度 | 输出研究简报、研究单元、证据整理、报告生成、发布校验等阶段 | 长任务像“卡死”，容易被用户中断 |
| P2 | 终端内容截断 | 提供详情视图或在窄终端自动换行 | 用户无法完整核对范围和任务编号 |
